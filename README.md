# Система управления библиотекой на микросервисах

Учебный проект демонстрирует микросервисную архитектуру на Spring Boot, отдельное владение данными, REST-контракты и автоматическое обнаружение сервисов через Eureka.

## Что такое микросервис и зачем он нужен

Микросервис — небольшое независимо развёртываемое приложение, реализующее законченную бизнес-возможность и общающееся с другими сервисами по формальному контракту. Такой подход позволяет независимо разрабатывать, выпускать и масштабировать части системы.

Преимущества:

- **масштабируемость** — можно увеличить число экземпляров только нагруженного сервиса;
- **гибкость** — сервисы можно изменять и выпускать независимо;
- **независимость** — сбой или обновление одного компонента не обязаны останавливать всю систему;
- **технологическая свобода** — сервисы могут иметь разные хранилища и внутреннюю реализацию.

У монолита единая кодовая база, процесс и часто одна база данных. По мере роста системы сборка и выпуск замедляются, небольшое изменение требует развёртывания всего приложения, трудно масштабировать одну функцию, а ошибка может затронуть весь процесс. При этом монолит проще на старте: микросервисы добавляют сетевые сбои, распределённые данные, мониторинг и сложность эксплуатации.

## Принципы проектирования

- **Слабая связность:** сервис знает публичный API соседа, но не его внутренние классы или таблицы.
- **Высокая согласованность:** вся логика одной бизнес-функции находится в одном сервисе.
- **Чёткая ответственность:** BookService управляет каталогом, UserService — читателями, BorrowService — выдачами.
- **Изоляция данных:** у каждого сервиса собственная H2-база; прямого доступа к чужим таблицам нет.
- **API как контракт:** взаимодействие идёт через явно определённые HTTP-эндпоинты и DTO.

## Архитектура

```text
Клиент
  ├── BookService   :8081 ── собственная БД booksdb
  ├── UserService   :8082 ── собственная БД usersdb
  └── BorrowService :8083 ── собственная БД borrowsdb
          │      │
          │      └── REST → UserService (проверка пользователя)
          └───────── REST → BookService (проверка и доступность)

Все сервисы регистрируются в Eureka Server :8761.
BorrowService обращается к именам book-service и user-service,
а Spring Cloud LoadBalancer выбирает их реальные экземпляры.
```

## Состав проекта

- `eureka-server` — реестр сервисов;
- `book-service` — CRUD книг и изменение доступности;
- `user-service` — CRUD пользователей;
- `borrow-service` — выдача, список операций и возврат книг.

Используются Java 17, Spring Boot 3.5.16, Spring Cloud 2025.0.1, Spring Web, Spring Data JPA, H2, DevTools, Eureka Client и LoadBalancer. Java 17 выбрана как минимальная переносимая версия; проект также запускается на установленной Java 25.

## Запуск

Откройте четыре терминала в корне проекта и запускайте приложения в этом порядке:

```powershell
.\mvnw.cmd -pl eureka-server spring-boot:run
.\mvnw.cmd -pl book-service spring-boot:run
.\mvnw.cmd -pl user-service spring-boot:run
.\mvnw.cmd -pl borrow-service spring-boot:run
```

Панель Eureka: <http://localhost:8761>. В ней должны появиться `BOOK-SERVICE`, `USER-SERVICE` и `BORROW-SERVICE`.

## Проверка API через curl

PowerShell использует `curl.exe`, чтобы команды не обрабатывались как `Invoke-WebRequest`.

Создать книгу:

```powershell
curl.exe -X POST http://localhost:8081/books -H "Content-Type: application/json" -d '{"title":"Domain-Driven Design","author":"Eric Evans","available":true}'
```

Создать пользователя:

```powershell
curl.exe -X POST http://localhost:8082/users -H "Content-Type: application/json" -d '{"name":"Ada Lovelace","email":"ada@example.com"}'
```

Выдать книгу (для первых созданных сущностей идентификаторы равны `1`):

```powershell
curl.exe -X POST http://localhost:8083/borrows -H "Content-Type: application/json" -d '{"bookId":1,"userId":1}'
```

После выдачи `GET http://localhost:8081/books/1` вернёт `"available":false`. Повторная выдача ответит HTTP 409. Вернуть книгу:

```powershell
curl.exe -X POST http://localhost:8083/borrows/1/return
```

Полезные эндпоинты:

| Сервис | Метод и путь | Назначение |
|---|---|---|
| Book | `GET /books`, `GET /books/{id}` | список и одна книга |
| Book | `POST /books`, `PUT /books/{id}`, `DELETE /books/{id}` | CRUD книги |
| Book | `PUT /books/{id}/availability` | изменить доступность |
| User | `GET /users`, `GET /users/{id}` | список и пользователь |
| User | `POST /users`, `PUT /users/{id}`, `DELETE /users/{id}` | CRUD пользователя |
| Borrow | `GET /borrows`, `GET /borrows/{id}` | история выдач |
| Borrow | `POST /borrows` | выдать книгу |
| Borrow | `POST /borrows/{id}/return` | вернуть книгу |

## UserService ↔ BorrowService

При выдаче BorrowService синхронно вызывает `GET /users/{id}`. Ответ 200 подтверждает существование читателя; 404 отклоняет выдачу. В крупной системе публичные сведения пользователя можно получать этим REST-вызовом, а изменения статуса пользователя распространять событиями через Kafka/RabbitMQ. Это уменьшит связанность и нагрузку на синхронную цепочку.

## Что учитывать при масштабировании

- **Гонки выдачи:** два экземпляра BorrowService могут одновременно увидеть книгу свободной. В production нужен атомарный контракт резервирования в BookService или saga с идемпотентными командами.
- **Частичные сбои:** BookService может изменить доступность, а сохранение выдачи — завершиться ошибкой. В примере есть компенсирующий возврат доступности, но надёжнее transactional outbox/saga.
- **Таймауты и повторы:** для сетевых вызовов нужны ограниченные таймауты, retry только для идемпотентных операций и circuit breaker.
- **Балансировка:** Eureka и Spring Cloud LoadBalancer распределяют вызовы между экземплярами, но БД также должна выдерживать параллельную работу.
- **Согласованность:** отдельные БД исключают обычную общую транзакцию; данные согласуются в итоге.
- **Наблюдаемость:** необходимы correlation ID, централизованные логи, метрики и распределённая трассировка.
- **Безопасность:** API Gateway/OAuth2, авторизация операций и защита внутренних контрактов.

REST выбран для наглядности и совместимости. gRPC уместен для частых внутренних вызовов с жёсткой схемой и меньшими накладными расходами, но потребует `.proto`-контрактов и отдельного инструментария.
